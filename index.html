中兴通讯 · 外派智利 · 光网络交付

通信设备升级 Agent Harness v0.2 原型

在智利做光网络交付、守夜间维护窗口的那段时间，我抽象出了第一个代表项目。

设备升级有相对稳定的操作链：预检、上传、安装和验证。真正需要工程判断的时刻，往往发生在标准流程出现偏差之后。安装失败时，工程师要结合设备状态、业务影响和剩余窗口决定下一步。

先前对启动升级的批准，并不自动包含回滚授权。

基于这一点，我把自然语言交互、动作决策和设备执行拆开设计。OpenClaw Agent 负责理解升级目标、查询状态和提出动作；所有执行请求经过类型化工具进入 Python 状态机，由状态机校验前置条件、任务状态及对应授权，再交给设备适配器执行。

模型提出的动作，在什么条件下可以执行？

值一次夜班：你来当批准人

浏览器里按同一套规则重做的演练 · 设备是 Mock · 数据为合成

三样东西，分开存放

这套 Harness 中，我把会话上下文、任务状态和执行证据分别处理。SQLite 保存任务当前所处的状态，request_id 用于保证重复建单请求的幂等性，追加式 JSONL 事件流记录工具调用、执行结果、人工批准和异常。这样，即使对话上下文被裁剪，系统仍然可以从持久记录回答“设备走到了哪一步”“谁批准了哪个动作”。

我在 v0.2 原型中接入 OpenClaw，通过 Mock 设备适配器注入安装和验证故障，检验单设备流程能否在正确的位置停下、等待独立的回滚授权，并留下可回放的执行轨迹。上面这台演练机做的是同一件事。

百度 · 训练推理

自进化排障智能体「北辰」

进入百度后，我开发了面向 Prefill/Decode 分离推理引擎的自进化排障智能体「北辰」。

这个场景的难点是故障症状高度共性。detokenizer 心跳停止、就绪探针返回 503，可能同时出现在内存耗尽、MoE 专家并行组重配置、RDMA 资源耗尽或 KV 传输异常等事件中。

我把系统职责划分为主理人、诊断专家和复盘专家。

  1. 主理人处理每轮入口与任务路由
  2. 诊断专家按故障域并行调用取证工具
    • 日志
    • 服务指标
    • 节点指标
    • Pod 生命周期
    • 单请求轨迹
    • 对应版本源码
  3. 复盘专家用户确认诊断结束后，登记真实根因与反馈

角色之间传递的是目标实例时间窗证据来源取数状态待验证假设

这样，后续判断能追溯到具体观测。

多个故障能产生相同症状时，系统凭什么确认根因？

证据门禁：证据到哪一步，结论就说到哪一步

北辰的核心设计，是把每类根因需要满足的证据条件写成可执行的门禁。排查 EP 组故障，要联合核对 worker 心跳、缩容或重配置事件以及请求路由变化；怀疑 RDMA 队列对（QP）耗尽，则要完成相关排除检查，并取得故障节点的 QP 实测。

若节点查询超时，报告仍可确认“该实例未通过就绪检查”，但对“QP 耗尽”的判断最多到“疑似”。我把这种确定性落实到每一条结论上：同一份结构化证据先生成供值班人员阅读的九行简报，再渲染附有证据、未决项和验证方法的完整报告。

慢在哪一段

我也为取证过程加入分段打点，按时间区间并集计算并行工具的实际占用，以区分数据源慢、模型耗时和编排往返过多这几类不同的优化问题。

北辰 · 自进化评测

我为什么把一轮评测判作无效？

复查样本时，我发现部分任务描述已经透露了故障类别。北辰只要读到题面，就可能猜中答案。那一轮的分数无法说明诊断策略有没有改进，我把结果判作无效。

我把类别标签留在评分侧，再按案例族切分数据集。现在，每份 Skill 补丁先经过修改范围、语法和 diff 审查，再与旧版在同一批冻结取证包上回放，比较故障命中、误报和证据缺失时给出“未知”的表现。开发集主指标严格优于基线后，候选才进入人工确认。

正在开发

基于自研 AI 编程助手的推理研发工作台插件

把这些经验用于需要多轮修改和实验的研发任务。Agent 根据目标组织实验，CLI 管理任务状态和轮次，独立验收器根据真实退出码、主指标、阈值及硬约束判定结果。

压测正常退出但缺少主指标时，本轮进入 blocked，记录需要补采的证据；数据有效但未达标时，失败原因进入下一轮。每份结果还绑定执行批次和轮次标识，防止任务重开后，旧执行的迟到结果覆盖当前结论。

沿着这条方向，我希望进一步量化 Agent 自身的工程收益：增加一次取证、一次模型调用或一轮复盘，究竟纠正了多少误判，又让工程师多等了多久。
